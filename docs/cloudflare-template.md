# Submitting Hedge to `cloudflare/templates`

The runbook for epic #54. Everything Hedge controls is generated by `scripts/build-template.ts`;
this file is the part that happens in *their* repository, plus the measurements and the caveats worth
stating before a reviewer finds them.

The submission is **a flattened copy generated from this repository**, never a second copy anyone
maintains. `cloudflare/templates` is a pnpm workspace of single-package directories: one
`package.json` npm can install, one `wrangler.jsonc`, one `dev` script their Playwright harness
starts with `npm run dev`. Hedge is a Bun workspaces monorepo with five packages and `workspace:*`
dependencies. A hand-maintained copy would drift within one release, and a template in Cloudflare's
gallery that is three releases behind is worse than no template.

## Generate

```sh
bun run build:template                 # writes hedge-cms-template/ (gitignored)
bun run build:template -- --install    # …then npm install, wrangler types, and the template's check
```

`--install` is **required before submitting** and needs the network. Two of the files that must be
committed into their repository can only be written by the tools that own them:

| File | Written by | Why it cannot be generated |
| --- | --- | --- |
| `package-lock.json` | `npm install` | Their `check:lockfiles` lints it, and CONTRIBUTING says a lockfile cuts Workers CI module resolution by 80% |
| `worker-configuration.d.ts` | `wrangler types` | Its runtime types follow the compatibility date, which the template downgrades to theirs |

The generator refuses to finish if its output would fail their linter: `scripts/template-lib.ts`
carries a transcription of `cli/src/lint.ts`, and `scripts/template-lib.test.ts` holds the generator
to it on every commit. That is a copy of somebody else's rules — **re-read theirs at submission
time**, because both the rules and the compatibility date move:

```sh
curl -s https://raw.githubusercontent.com/cloudflare/templates/main/cli/src/lint.ts \
  | grep -E 'TARGET_COMPATIBILITY_DATE|integrationsPlatCategories'
```

## Drive their CI gate

Their whole gate is one script:

```
check = check:templates && check:lockfiles && check:turbo && check:prettier && git diff --exit-code
```

Three of those four are about their toolchain rather than template metadata, and the trailing
`git diff --exit-code` fails if any of them wrote a file. The sequence:

```sh
git clone https://github.com/cloudflare/templates
cp -R /path/to/hedge-cms/hedge-cms-template templates/
cp /path/to/hedge-cms/templates/hedge-cms-template.spec.ts templates/playwright-tests/
cd templates
rm -rf hedge-cms-template/node_modules            # theirs, from their pnpm install
pnpm install
pnpm fix:lockfiles                                # regenerates hedge-cms-template/package-lock.json
pnpm check                                        # the gate
pnpm test:e2e -- --grep hedge                     # the smoke test
```

If `pnpm check` fails on formatting, `pnpm fix` is their own escape hatch — but it should not, because
the generator formats its output with Prettier using the `.prettierrc.yaml` it writes into the
template directory. That file is deliberate: Prettier is not Biome, so a directory formatted by ours
fails `prettier . --check` at their root. A per-template config is the nearest one Prettier finds for
these files and `saas-admin-template` set the precedent.

Record anything that has to change **outside** `hedge-cms-template/` — a shared dependency bump, a
`.prettierrc.yaml` override, a `syncpack` alignment — because those belong in the PR description.

## The gate, driven (#52)

Run on 2026-08-09 against a fresh clone of `cloudflare/templates` (`3c583a2`) with the generated
directory and the spec dropped in, following the sequence above.

| Their command | Result |
| --- | --- |
| `pnpm install` (whole workspace, 41 templates) | passes, 3m54s. No peer warning names `hedge-cms-template` |
| `pnpm check:templates` | passes |
| `pnpm fix:lockfiles` → `pnpm check:lockfiles` | passes. Only *our* lockfile is rewritten |
| `pnpm check:turbo` (`turbo run check cf-typegen --force`, 79 tasks) | passes. Ours takes 13.5s |
| `pnpm check:prettier` | passes — **after the two fixes below** |
| `git diff --exit-code` | clean |
| **`pnpm -w check`** | **exits 0** |
| `pnpm -w test` (`turbo run test`) | passes, 13 tasks |
| `pnpm test:e2e --grep hedge` | **3 passed**, 8.1s — see the port note below |

**Nothing outside `hedge-cms-template/` had to be hand-edited.** Two tracked files change and both are
written by their own tooling: `pnpm-lock.yaml`, and `templates.json`, which gains a
`package_json_hash` entry for us. Both belong in the PR. The `.prettierrc.yaml` override this issue
anticipated needing in *their* repo is not needed — ours lives inside the template directory, which
is the nearest config Prettier finds.

`pnpm check:deps` (syncpack) is **not** part of `check` and does not gate a PR: `pull-request-deps.yaml`
runs `fix:deps` and commits the result. It already fails on their `main` for three unrelated
templates. Ours raises the highest pinned version of `@types/node` (24.13.3 vs 24.10.1),
`@tailwindcss/vite` (4.3.3 vs 4.1.17), `wrangler` (4.114.0 vs 4.88.0) and three Radix packages, so
expect their bot to align some of those — which is a dependency bump for us, not a template change.

### Two things their CI found that nothing here could

- **Prettier's version is part of the contract.** The generator formatted with a bare
  `bunx prettier`, which resolves the newest release (3.9.6); their repo pins **3.7.4**, and the two
  disagree about one union type in `src/auth/forward.ts`. The directory was clean here and failed
  `check:prettier` there. `TEMPLATE_PRETTIER_VERSION` in `scripts/template-lib.ts` now pins it —
  re-read it alongside the compatibility date at submission time.
- **Their harness sets no `baseURL`.** `playwright.config.ts` has none, so `page.goto("/")` throws
  "Cannot navigate to invalid URL"; every navigation goes through the `templateUrl` fixture, which is
  *also* what starts the server — a test that doesn't request it only passes when an earlier test in
  the file booted one. Both were written into the spec from reading `fixtures.ts`, and both were
  wrong.

### The port, and how to run their harness when 5173 is taken

`pnpm test:e2e --grep hedge` reports **3 passed** — their fixtures, their server manager, a cold
`.wrangler`, `.dev.vars.example` copied in by the harness, well inside the 30-second budget.

The port is the one thing worth knowing. Their harness picks it by framework heuristic (`vite` in the
dependency set → 5173) and polls it, and **the poll cannot tell our server from anybody else's**: with
an unrelated Vite dev server already on 5173, `wrangler dev` fails to bind and the harness happily
reports ready against the stranger — the health assertion passed against a different application
(`{"status":"ok","version":"0.68.1"}`) and only the navigations gave it away. A CI runner has the port
free, so this is a local collision rather than a template defect.

To run it locally anyway, patch the scratch checkout — never the generated directory:

```sh
# playwright-tests/utils/template-server.ts, in the vite branch
port = Number(process.env.E2E_VITE_PORT ?? 5173);
# hedge-cms-template/package.json, in `dev`
wrangler dev --port ${E2E_VITE_PORT:-5173} …
E2E_VITE_PORT=5211 pnpm test:e2e --grep hedge
```

Revert both afterwards; the committed template must keep binding the port their heuristic picks.

## What has been verified here, and what has not

Measured on this repository's own runner, against the generated directory:

| Check | Result |
| --- | --- |
| `npm install` with no Bun installed | passes, 265 packages |
| `npm run build` (Vite build of the admin) | passes, ~9s, 1.4 MB of assets |
| `npm run check` (`build` → both `tsc` projects → `wrangler deploy --dry-run`) | passes |
| `npm run cf-typegen` | passes |
| `npm run dev` → first `200` from `/api/health` | **~19s** cold, against their 30s budget |
| First-run wizard through to the admin, in a real browser | passes |
| `prettier --check` over the generated directory | clean |

`prettier --check` here is necessary and not sufficient: it is their pinned version that decides, and
only a run in their checkout uses it. See the gate section above.

### The 30-second budget, and why `dev` looks the way it does

Their harness (`playwright-tests/utils/template-server.ts`) spawns exactly `npm run dev` and polls
for 30 seconds. Run in sequence, Hedge does not fit:

| Step | Cold |
| --- | --- |
| `wrangler d1 migrations apply DB --local` (15 migrations) | ~12.5s |
| `vite build` | ~9.2s |
| `wrangler dev` to first health check | ~7s |
| **Sequential total** | **~30.3s** — over budget |

The migration and the build are independent, so the template's `dev` runs the migration in the
background and collects it with `wait`: **~19s** across three cold runs — and **~29s** on the one run
measured immediately after `npm install`, with the page cache still cold. That is the real headroom,
and it is not generous. Re-measure before adding anything to that line, and expect their CI to sit
nearer the slow end than the fast one.

The harness also picks the port **by framework heuristic, not from our script**: `vite` anywhere in
the dependency set means 5173. The admin build needs vite, so `wrangler dev --port 5173` it is.

### Two things that fail silently, and cost a day each if rediscovered

- **The admin's tsconfig has to live in `admin/`.** Vite hands each file to esbuild with the options
  from the *nearest* `tsconfig.json`. With only a root config — which the Worker needs, and which
  sets `jsxImportSource: "hono/jsx"` — the admin's `.tsx` compiles against Hono's JSX runtime. The
  build succeeds, `tsc` succeeds, and the page throws `Cannot convert a Symbol value to a string` out
  of `JSXNode` with a blank screen and nothing in any log.
- **`.dev.vars.example` is not documentation here.** The harness copies it to `.dev.vars` and never
  generates one, so an empty `AUTH_SECRET` 500s every authenticated route and reads as a bug in
  Hedge rather than a missing value.

### One npm/bun divergence, pinned in the generator

`@hookform/resolvers` is pinned to `5.2.2` rather than the `5.4.2` this repository resolves. 5.4.x
declares an optional peer on `@typeschema/main`, whose `@typeschema/valibot` wants valibot `^0.39`
while the resolver itself wants `^1` — bun installs it, npm reports `ERESOLVE` and stops.
`NPM_RESOLUTION_OVERRIDES` in `scripts/build-template.ts` is where that lives; keep the list short
and the reason written down, because each entry is a divergence from what this repository tests.

## The Playwright spec

`templates/hedge-cms-template.spec.ts` is committed here and copied into their `playwright-tests/`.
**The filename is load-bearing**: `fixtures.ts` derives the template name from it, so any other name
fails with "template not found".

**Every test takes the `templateUrl` fixture and navigates through it.** Their `playwright.config.ts`
sets no `baseURL`, and `templateUrl` is also what starts the server — a test that omits it fails with
"Cannot navigate to invalid URL", or passes only because a neighbour booted the server first.

It covers three things and deliberately no more — `/api/health`, the first-run wizard rendering, and
completing the wizard. Collections, media, entry workflow and MCP are covered by this repository's
own suite, and spending someone else's CI on them is rude.

Nothing in it signs in with a password. A correct password from a browser the account has never been
seen on produces a six-digit code rather than a session (`.claude/rules/auth.md`), and every
Playwright browser is an unrecognised device. The wizard is exempt because it creates the session
itself.

## Before opening the PR

**1. Deploy a public preview.** A real Hedge on `workers.dev` with D1, R2 and Email Sending
provisioned, seeded with a small demo site so the admin is not empty. Their convention is
`https://<template-name>.templates.workers.dev`, which is *their* host and only exists once the
template is published — so put our own deployment behind the link in the README for the PR and let
the reviewer swap it. Their `validate-live-demo-links` job checks it resolves.

Decide up front what happens when a visitor edits the demo content: either accept it, or reset it on
a schedule. The README's live-preview link is `templates/README.template.md`; change it there, not in
the generated copy.

**Step-up verification is what makes "credentials a reviewer can use" hard, and it has to be solved
before the link is worth clicking.** A correct password from a browser the account has never been
seen on does not produce a session — it produces a six-digit code mailed to the address on the
account (`.claude/rules/auth.md`), and every reviewer is an unrecognised device. Two consequences,
and the second is the one that bites:

- With no sender configured the mail is composed and logged, never sent (`email/send.ts`), so the
  code does not exist anywhere a reviewer can reach. They get as far as the login screen.
- **Configuring Email Sending does not fix it by itself.** The code goes to the *demo owner's*
  mailbox, which a reviewer has no access to either. A shared demo account needs a mailbox the
  reviewer can read — seed the owner at an address on a public inbox and say so beside the
  credentials — or the preview is look-but-don't-touch.

Also seed the first owner immediately after deploying. Until somebody completes the wizard, the
deployment has no owner and the first visitor to reach `/` can claim it.

**2. Open the "template idea" issue on `cloudflare/templates` first.** CONTRIBUTING opens by inviting
exactly that. A rejected issue costs a day; a rejected PR costs the effort. Say what Hedge is, that it
features D1 + R2 + Email Sending in one Worker — the multi-binding combination CONTRIBUTING says they
are especially interested in — link the preview, and state the caveats below rather than letting them
be discovered.

**3. State the caveats ourselves.**

- **Size.** This is a product, not a starter, and would be the largest thing in the gallery.
  The counter: `saas-admin-template` and `r2-explorer-template` are applications too, and a CMS is
  the canonical "can Workers host this?" question. Expect our install, `check` and E2E boot to be the
  slowest in the repository, and say so with the numbers above rather than being told.
- **Scope not shipped.** The template drops `apps/installer` — a local wizard for repository-less
  installs, meaningless inside a template someone clicks Deploy on. `packages/deploy` still ships
  because the Worker imports it for the dashboard update path.
- **The rename.** Their linter forces the Worker to be `hedge-cms-template`, so the template sets
  `WORKER_NAME` to match; without it the in-dashboard updater would address a script called
  `hedge-cms` that does not exist. The reasoning is in `.claude/rules/workers-config.md`.
- **Compatibility date downgrade.** We pin newer than their `TARGET_COMPATIBILITY_DATE`. Nothing in
  the Worker depends on a behaviour newer than theirs — `nodejs_compat` is the only flag — and say
  that we checked.

**4. Open the PR** against `main` with CONTRIBUTING's checklist filled in, and ask in the description
for `preview_image_url` and `preview_icon_url`. Those can only be issued by a Cloudflare team member
from their images account, so the PR lands without them by design. Do not set `cloudflare.publish`;
that is theirs to turn on.

## After it lands

Their `templates.json` records a `package_json_hash` per template and their CI deploys live demos, so
a template that stops matching this repository is a bad advert. The generator is most of the answer;
the rest is the release checklist in `.claude/rules/workers-config.md`, which now says to regenerate
and re-submit when cutting a release.
