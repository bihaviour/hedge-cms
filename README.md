# Hedge

**HEDGE (Headless + Edge) CMS.** Content management that runs entirely on Cloudflare's edge — no origin
server, no container, no cold starts. One Worker serves the admin UI, the management API, and a
cached read-only delivery API.

[![Deploy to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https://github.com/bihaviour/hedge-cms)

> Status: early scaffold. The foundation below works end to end; features are being deepened.

## Stack

| Concern      | Choice                                                     |
| ------------ | ---------------------------------------------------------- |
| Runtime      | Cloudflare Workers                                         |
| Toolchain    | Bun (package manager, test runner, scripts)                |
| API          | Hono + Zod                                                 |
| Database     | Cloudflare D1 (SQLite) via Drizzle ORM                     |
| File storage | Cloudflare R2                                              |
| Email        | Cloudflare Email Sending (`send_email` binding)            |
| Admin UI     | React 19 + Vite + Tailwind v4 + shadcn/ui                  |
| Lint/format  | Biome                                                      |

## What's here

- **Sites** — one deployment holds many websites: a blog, a docs site, a landing page. Each is
  its own namespace for collections, entries, media, API keys and members.
- **Users and members** — two separate account types. A **User** operates the CMS; a **Member**
  is a visitor of one site who signs in on that site to unlock gated content, and can never
  reach the admin.
- **Per-site roles** — owners and admins run the instance and reach every site; editors and
  viewers only reach the sites they are granted, at the role they are granted.
- **Auth** — [Better Auth](https://www.better-auth.com) on both sides: signed session cookies for
  operators, bearer tokens for website members, and OAuth 2.1 for MCP clients. A first-run
  onboarding wizard, emailed invites, password reset, email verification, revocable sessions, and
  rate limiting backed by D1. Nobody ever sets somebody else's password: users and members alike
  are added by email and choose their own.
- **Collections** — user-defined content types. Twelve field kinds (text, richtext, number,
  boolean, date, select, media, reference, url, email, color, json), edited in the admin and
  enforced on write.
- **Entries** — draft/published/archived, public or members-only, per-locale, keyset-paginated,
  with an automatic revision snapshot on every update.
- **Media** — uploads to R2 with type and size limits, served from `/media/*` with immutable
  cache headers so repeat hits never touch the bucket.
- **Delivery API** — `/api/v1/content/*`, published content only, `s-maxage` cached at the edge,
  authenticated with scoped per-site API keys.
- **MCP** — an AI assistant can run the whole CMS over OAuth 2.1: collections, entries, media,
  newsletters, sites, users and keys, bounded by scopes you approve *and* your own role.

## Repository layout

```
apps/
  api/            Cloudflare Worker — API, media serving, admin asset hosting
    src/routes/   auth · users · sites · members · api-keys · collections · entries · media · content · mcp
    src/lib/      The services behind the routes, shared with the MCP tools
    src/mcp/      MCP tool definitions, one module per area of the CMS
    src/auth/     The two Better Auth instances — operators (with OAuth for MCP) and members
    src/db/       Drizzle schema and client

packages/

```

## Deploy your own

[![Deploy to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https://github.com/bihaviour/hedge-cms)

The button forks this repository into your GitHub or GitLab account, creates the D1 database and R2
bucket it needs, builds the Worker and deploys it. The only thing to type is `AUTH_SECRET` — a long
random string, `openssl rand -base64 32` will do. Every later push to your fork redeploys.

You land on `https://hedge-cms.<your-subdomain>.workers.dev`, in the onboarding wizard, where you
create the owner account and the first site. Nothing else is required to start writing content.

Two things are worth doing next, when you need them:

- **Email.** Invites, password resets and newsletters send through Cloudflare Email Sending, which
  needs a domain of yours onboarded first: `bunx wrangler email sending enable yourdomain.com`.
  Until then those sends fail — the address they send from is set under **Settings → Email**, and a
  site can send its own newsletters and member email as itself by setting a sender under **Site
  settings**. Operator invites and password resets always use the deployment's.
- **A custom domain.** Add the route in the Cloudflare dashboard, then set the `PUBLIC_URL` variable
  to that URL. Left empty, the deployment answers with whatever origin the request arrived on, which
  is right for the generated workers.dev URL and for local development but not for a Worker reached
  by two hostnames.

  `PUBLIC_URL` must be a **full origin, scheme included** — `https://cms.example.com`, not
  `cms.example.com`, and no trailing slash. Authentication is built from this value, so a bare
  hostname is not a near miss: it is rejected outright and every sign-in and admin request answers
  500, while `/api/health` keeps returning `ok` because it never touches auth.

R2 must be enabled on the account, since media lives there.

## Keeping a deployment up to date

Your deployment is a fork, and every push to it redeploys, so updating is a **Sync fork** on GitHub
or GitLab: pull this repository's new commits into your fork and Workers Builds rebuilds and applies
any new database migrations on the way. Nothing else to run.

The admin knows when there is something to sync. **Settings → About & updates** shows the version the
deployment runs and, when this project has cut a newer release, a banner and the steps to take it.
Set the `REPO_URL` variable to your fork's URL and that page links straight to its sync button —
otherwise it links to the release notes.

## Getting started locally

Requires [Bun](https://bun.sh) 1.3+. No Cloudflare account: `wrangler dev` emulates D1, R2 and the
assets binding on your machine.

```bash
bun install

# Local secrets
echo 'AUTH_SECRET="'$(openssl rand -base64 32)'"' > .dev.vars

bun run db:migrate          # apply migrations to the local D1
bun run db:seed             # optional sample collection and entries
```

Run the two dev servers in separate terminals:

```bash
bun run dev:api             # Worker on http://localhost:8787
bun run dev:admin           # Admin UI on http://localhost:5173 (proxies /api to the Worker)
```

Open http://localhost:5173. A deployment with no users starts in the onboarding wizard: it creates
the owner account, then the first site. Nothing is created behind your back — a fresh database has
no site until you name one, and an interrupted setup picks up where it left off when you sign in.

In development, emails are not sent — invite and reset links are printed to the `dev:api`
console so you can follow them locally.

## Deploying from your machine

The button above is the short path; this is the same deployment done by hand.

```bash
bunx wrangler secret put AUTH_SECRET
bunx wrangler email sending enable yourdomain.com   # required before any email is sent
bun run deploy                                      # build, migrate the remote D1, deploy
```

The D1 database and R2 bucket are created on the first deploy — `wrangler.jsonc` names them but
carries no ids, which is what lets anyone deploy this repository into their own account unedited.
`PUBLIC_URL` and `EMAIL_FROM` are the two variables worth setting there once the deployment has a
domain; `PUBLIC_URL` is what invite, reset and media links point at.

## Using the delivery API

Create a key in **Settings → API keys** with the `content:read` scope, then:

```bash
curl https://your-worker.workers.dev/api/v1/content/posts \
  -H "Authorization: Bearer hdg_..."
```

| Endpoint                              | Returns                                     |
| ------------------------------------- | ------------------------------------------- |
| `GET /api/v1/content/:collection`     | Published entries, paginated via `nextCursor` |
| `GET /api/v1/content/:collection/:slug` | A single published entry                  |
| `GET /api/v1/content/:collection/_schema` | The collection's field definitions       |

Query parameters: `locale`, `limit`, `cursor`, `sort`, `order`.

A key belongs to the site it was created on and can only read that site's content, so nothing
extra is needed to pick a tenant.

## Writing content from a script

A key with a **write** scope also reaches the authoring routes, so an import or another service can
create content without a person's password:

```bash
curl -X POST https://your-worker.workers.dev/api/v1/collections/posts/entries \
  -H "Authorization: Bearer hdg_..." -H 'content-type: application/json' \
  -d '{"slug":"hello","status":"published","data":{"title":"Hello"}}'
```

| Scope | Reaches |
| ----- | ------- |
| `content:read` | The delivery API — published entries only |
| `content:write` | Creating, editing and deleting entries |
| `media:read` / `media:write` | Listing media, and uploading or deleting it |
| `collections:write` | Creating, changing and deleting collections |

An authoring key wants `content:read` **and** `content:write`: the first is what lets it read back
what it wrote, including drafts.

A key with no write scope is confined to the delivery API and never sees a draft — that is the
credential a public website holds, and the separation is enforced by which middleware runs on which
path prefix, not by each route remembering to check. **No key of any kind** reaches users, sites,
members, email, or the API key routes themselves; those need a signed-in person.

## Managing the CMS over MCP

Hedge exposes a [Model Context Protocol](https://modelcontextprotocol.io) server so an AI assistant
can run the CMS directly — not just draft a post, but define the content model it lives in, caption
the media it references, write the email template that announces it, and manage who has access. It
is a single Streamable-HTTP endpoint on the Worker — no separate process — speaking JSON-RPC 2.0,
with **48 tools** grouped into read/write scope pairs:

| Area | Tools | Scopes |
| ---- | ----- | ------ |
| Collections | List, read, create, update, delete the content model | `collections:read` / `collections:write` |
| Entries | List, read, draft, publish, delete, plus revision history and restore | `entries:read` / `entries:write` |
| Media | List and read uploads; edit alt text and filenames; delete | `media:read` / `media:write` |
| Newsletters | Email templates, campaign drafts, subscribers, test sends | `newsletters:read` / `newsletters:write` |
| Sites | List and read sites; create, configure and delete them | `sites:read` / `sites:write` |
| Users | List, invite, change roles, remove; grant and revoke per-site access | `users:read` / `users:write` |
| API keys | List, issue and revoke a site's keys | `keys:read` / `keys:write` |

Two things the REST API can do are deliberately left out:

- **Sending a newsletter to its audience.** It reaches real inboxes and cannot be recalled, so it
  stays a decision a person makes in the admin. `send_test_newsletter` mails one address you name,
  which is what an assistant actually needs to check its work.
- **Uploading media.** It needs a multipart body streamed into R2, and base64 through a model's
  context window is not a substitute. Everything *about* an upload is exposed; the bytes arrive
  through the admin or `POST /api/v1/media`.

One thing worth knowing before you grant it: `create_api_key` returns a raw secret, which lands in
the assistant's context and whatever transcript its client keeps. That is a weaker place than the
admin's show-once dialog. Withhold `keys:write` unless you want that.

### Connecting a client

Authentication is **OAuth 2.1** — no key to paste. Point the client at the URL and it discovers the
rest: it reads the protected-resource metadata, registers itself, and opens a browser for you to
sign in and approve it.

```bash
claude mcp add hedge --transport http https://your-worker.workers.dev/api/v1/mcp
```

```jsonc
{
  "mcpServers": {
    "hedge": {
      "type": "http",
      "url": "https://your-worker.workers.dev/api/v1/mcp"
    }
  }
}
```

What happens behind that, and where each piece lives:

| Step | Endpoint |
| ---- | -------- |
| Discover the resource | `GET /.well-known/oauth-protected-resource` |
| Discover the authorization server | `GET /.well-known/oauth-authorization-server` |
| Register the client (RFC 7591) | `POST /api/v1/auth/mcp/register` |
| Sign in and approve | `GET /api/v1/auth/mcp/authorize` → `/oauth/consent` |
| Exchange the code (PKCE, S256) | `POST /api/v1/auth/mcp/token` |

An unauthenticated request is answered with `401` and a `WWW-Authenticate: Bearer
resource_metadata="…"` challenge, which is what lets a client bootstrap from the URL alone.

Every authorization request goes through the consent screen even when the client does not ask for
one — a token that can rewrite your content model should never arrive from a redirect nobody read.
Access tokens last an hour; ask for the `offline_access` scope to get a refresh token. You can see
what you have approved, and revoke it, under **Settings → Account**.

### What a client is allowed to do

A token acts as the user who approved it, so it is limited **twice over**: by the scopes granted at
the consent screen, and by that user's own role. Neither implies the other, and the narrower one
always wins.

That means the same MCP client gives different people different powers, with nothing to configure:

| The user approving it | What their client can do |
| --------------------- | ------------------------ |
| Viewer on the site | Read entries, collections and media |
| Editor on the site | Also draft, publish and delete entries; write newsletters and templates |
| Admin on the site | Also reshape collections, and issue that site's API keys |
| Instance admin | Also invite users, change their roles, and create sites |
| Owner | Everything, including deleting a site |

So granting `collections:write` to an editor's client does not let it rewrite schemas — the editor
could not either. And granting `users:write` to a site admin's client does not let it manage users,
because who may sign in to the deployment is not one site's business.

Roles are checked at whichever level the tool belongs to: content, media, newsletters and keys
against your role on the **active site**; users and creating or deleting sites against your role on
the **deployment**. Send the site with the `X-Hedge-Site` header when there is more than one.

A client is only shown the tools its scopes cover, so an assistant approved for reading never sees a
delete tool at all. Ask for a narrow set — a documentation assistant wants the `:read` halves and
nothing else, and then no prompt it is fed can talk it into a write.

Delivery API keys are deliberately **not** accepted here. The key that serves a public website sits
in that website's environment variables, which is the least protected place any Hedge credential
lives; it has no business rewriting content models.

## Roles

Two levels, deliberately separate — a site admin runs their site, not your instance.

| Level | Where it lives | Grants |
| ----- | -------------- | ------ |
| Instance | `users.role` | `owner` and `admin` manage users and sites, and reach every site. `editor` / `viewer` here is only the role a user is granted with by default. |
| Site | `site_users` | `admin` — the site's content, keys and members. `editor` — write content. `viewer` — read. |

For anyone below instance admin the grant *is* their access: no row, no site — it will not even
appear in their site switcher. Inviting an editor or viewer grants them the site you invited them
from; anything after that is handed out under **Settings → Users → Manage**.

Users are invited by email and set their own password, so an invited account shows as *pending*
until they do. The invite can be sent again from that row — and doing so spends the previous link,
so an invite forwarded to the wrong inbox stops working the moment a new one goes out.

## Members and gated content

Set an entry's visibility to **Members only** and the delivery API stops handing out its `data`.
It still appears in list responses, marked `"locked": true` and stripped of content, so a site can
render a teaser; the single-entry endpoint answers `403` instead.

Visitors sign in against their site and get a bearer token to replay:

```bash
# The site is picked with the X-Hedge-Site header (a site slug), or by the request's Host
# when the site has a domain set.
curl -X POST https://your-worker.workers.dev/api/v1/member/login \
  -H 'content-type: application/json' -H 'X-Hedge-Site: blog' \
  -d '{"email":"reader@example.com","password":"…"}'
# → { "data": { "token": "…", "expiresAt": "…", "member": { … } } }

curl https://your-worker.workers.dev/api/v1/content/posts/members-only-deep-dive \
  -H "Authorization: Bearer hdg_..." -H "X-Member-Token: …"
```

| Endpoint                                    | Does                                        |
| ------------------------------------------- | ------------------------------------------- |
| `POST /api/v1/member/register`              | Sign up, when the site allows it            |
| `POST /api/v1/member/login`                 | Exchange credentials for a token            |
| `POST /api/v1/member/logout`                | Revoke the presented token                  |
| `GET /api/v1/member/me`                     | The signed-in member                        |
| `POST /api/v1/member/forgot-password`       | Email a reset link                          |
| `POST /api/v1/member/reset-password`        | Set a new password from that link's token   |
| `POST /api/v1/member/send-verification-email` | Re-send the confirmation email            |

The token travels in `X-Member-Token`, not `Authorization` — a website sends both at once, its
delivery key identifying the site and the member token identifying the reader. It is rotated as the
member keeps using it, and register, login and reset are rate limited.

Registering sends a confirmation email. It is not required to sign in, but `emailVerified` is there
for a site that wants to gate on it. Reset links point at `https://<your site domain>/reset-password`
when the site has a domain set; pass `redirectTo` to choose another page on that same domain.

**Adding a member from the admin emails them a link.** There is no field for a password, because an
account a stranger knows the password to is not the reader's account. Until they follow that link
they show as *invited* in **Members**, and the invite can be sent again from the same row. Someone
who already reads another site in this deployment is simply granted this one — they keep the
password they have.

Responses that carry a member token are returned `private, no-store`, so gated content never lands
in a shared cache. Members have no access to the admin API at all — they authenticate against a
separate Better Auth instance over separate tables, so a member token is not merely refused there,
it cannot be resolved.

**One account, many sites.** A member identity belongs to the deployment, and `member_sites` records
which sites they may read. A reader of your blog who also reads your docs site keeps one password,
and a site can block them without touching their access to the other. Signing in to a second site
joins it when that site takes signups, and is refused when it is invite-only.
