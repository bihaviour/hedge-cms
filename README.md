# Hedge

**Headless + edge CMS.** Content management that runs entirely on Cloudflare's edge — no origin
server, no container, no cold starts. One Worker serves the admin UI, the management API, and a
cached read-only delivery API.

> Status: early scaffold. The foundation below works end to end; features are being deepened.

## Stack

| Concern      | Choice                                                     |
| ------------ | ---------------------------------------------------------- |
| Runtime      | Cloudflare Workers                                         |
| Toolchain    | Bun (package manager, test runner, scripts)                |
| API          | Hono + Zod                                                 |
| Database     | Cloudflare D1 (SQLite) via Drizzle ORM                     |
| File storage | Cloudflare R2                                              |
| Email        | Cloudflare Email Sending (`send_email` binding)            |
| Admin UI     | React 19 + Vite + Tailwind v4 + shadcn/ui                  |
| Lint/format  | Biome                                                      |

## What's here

- **Sites** — one deployment holds many websites: a blog, a docs site, a landing page. Each is
  its own namespace for collections, entries, media, API keys and members.
- **Users and members** — two separate account types. A **User** operates the CMS
  (`owner` › `admin` › `editor` › `viewer`); a **Member** is a visitor of one site who signs in
  on that site to unlock gated content, and can never reach the admin.
- **Auth** — session cookies with PBKDF2-hashed passwords, first-run owner setup, emailed
  invites, and password reset.
- **Collections** — user-defined content types. Nine field kinds (text, richtext, number,
  boolean, date, select, media, reference, json), edited in the admin and enforced on write.
- **Entries** — draft/published/archived, public or members-only, per-locale, keyset-paginated,
  with an automatic revision snapshot on every update.
- **Media** — uploads to R2 with type and size limits, served from `/media/*` with immutable
  cache headers so repeat hits never touch the bucket.
- **Delivery API** — `/api/v1/content/*`, published content only, `s-maxage` cached at the edge,
  authenticated with scoped per-site API keys.

## Repository layout

```
apps/
  api/            Cloudflare Worker — API, media serving, admin asset hosting
    src/routes/   auth · users · sites · members · api-keys · collections · entries · media · content
    src/db/       Drizzle schema and client
    migrations/   D1 migrations (generated by drizzle-kit)
  admin/          React admin UI, built to dist/ and served by the Worker
packages/
  core/           Zod schemas and types shared by both sides
```

## Getting started

Requires [Bun](https://bun.sh) 1.3+ and a Cloudflare account.

```bash
bun install

# Create the remote resources (once), then paste the printed ids into apps/api/wrangler.jsonc
bunx wrangler d1 create hedge-db
bunx wrangler r2 bucket create hedge-media

# Local secrets
echo 'AUTH_SECRET="'$(openssl rand -base64 32)'"' > apps/api/.dev.vars

bun run db:migrate          # apply migrations to the local D1
bun run db:seed             # optional sample collection and entries
```

Run the two dev servers in separate terminals:

```bash
bun run dev:api             # Worker on http://localhost:8787
bun run dev:admin           # Admin UI on http://localhost:5173 (proxies /api to the Worker)
```

Open http://localhost:5173 and create the owner account on the setup screen.

In development, emails are not sent — invite and reset links are printed to the `dev:api`
console so you can follow them locally.

## Deploying

```bash
bunx wrangler secret put AUTH_SECRET --env production
bunx wrangler email sending enable yourdomain.com   # required before any email is sent
bun run db:migrate:remote
bun run deploy
```

Set `PUBLIC_URL`, `EMAIL_FROM`, and `EMAIL_FROM_NAME` under `env.production.vars` in
`apps/api/wrangler.jsonc` before deploying — `PUBLIC_URL` is what invite and media links point at.

## Using the delivery API

Create a key in **Settings → API keys** with the `content:read` scope, then:

```bash
curl https://your-worker.workers.dev/api/v1/content/posts \
  -H "Authorization: Bearer hdg_..."
```

| Endpoint                              | Returns                                     |
| ------------------------------------- | ------------------------------------------- |
| `GET /api/v1/content/:collection`     | Published entries, paginated via `nextCursor` |
| `GET /api/v1/content/:collection/:slug` | A single published entry                  |
| `GET /api/v1/content/:collection/_schema` | The collection's field definitions       |

Query parameters: `locale`, `limit`, `cursor`, `sort`, `order`.

A key belongs to the site it was created on and can only read that site's content, so nothing
extra is needed to pick a tenant.

## Members and gated content

Set an entry's visibility to **Members only** and the delivery API stops handing out its `data`.
It still appears in list responses, marked `"locked": true` and stripped of content, so a site can
render a teaser; the single-entry endpoint answers `403` instead.

Visitors sign in against their site and get a bearer token to replay:

```bash
# The site is picked with the X-Hedge-Site header (a site slug), or by the request's Host
# when the site has a domain set.
curl -X POST https://your-worker.workers.dev/api/v1/member/login \
  -H 'content-type: application/json' -H 'X-Hedge-Site: blog' \
  -d '{"email":"reader@example.com","password":"…"}'
# → { "data": { "token": "hdm_…", "expiresAt": "…", "member": { … } } }

curl https://your-worker.workers.dev/api/v1/content/posts/members-only-deep-dive \
  -H "Authorization: Bearer hdg_..." -H "X-Member-Token: hdm_..."
```

| Endpoint                            | Does                                          |
| ----------------------------------- | --------------------------------------------- |
| `POST /api/v1/member/register`      | Sign up, when the site allows it              |
| `POST /api/v1/member/login`         | Exchange credentials for a token              |
| `POST /api/v1/member/logout`        | Revoke the presented token                    |
| `GET /api/v1/member/me`             | The signed-in member                          |

Responses that carry a member token are returned `private, no-store`, so gated content never
lands in a shared cache. Members exist per site and have no access to the admin API at all.

## Scripts

| Command                   | Does                                              |
| ------------------------- | ------------------------------------------------- |
| `bun run build`           | Build core, admin, and the Worker bundle           |
| `bun run deploy`          | Build, then deploy to the production environment   |
| `bun run test`            | Run the test suite                                 |
| `bun run typecheck`       | Typecheck every workspace                          |
| `bun run lint` / `lint:fix` | Biome check, optionally with fixes               |
| `bun run db:generate`     | Generate a migration from schema changes           |
| `bun run cf-typegen`      | Regenerate Worker binding types after config edits |
